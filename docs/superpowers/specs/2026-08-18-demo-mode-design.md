# Демо-режим «потрогать изнутри» (D-029) — дизайн

**Дата:** 2026-08-18 · **Статус:** утверждён владельцем сессии
**Источник:** mandate владельца D-029 (письмо brain `2026-08-15-demo-mode-all-roles-mandate`, high)

## Цель

Покупатель принимает решение внутри приложения, а видит сейчас только лендинг.
Демо-режим = публичная витрина: демо-филиал с полными выдуманными данными, вход
под каждой из пяти ролей с главной страницы без регистрации, живая работа
(создание сущностей, уведомления ролей), кнопка «Сменить роль» на каждой странице.

## Ключевые решения (утверждены)

| Развилка | Решение |
|---|---|
| Изоляция | **Демо-филиал в прод-БД** с флагами + явные гейты (не отдельный инстанс/схема) |
| Аккаунты | **Общие**: 5 фиксированных демо-юзеров, все посетители делят их |
| Сброс | **Ночной полный reseed** через cron-роут (ежедневно доказывает идемпотентность, #139) |
| «Бухгалтер» | Маппится на роль `admin` (админ филиала и есть бухгалтерия — PaymentThreads, доводка 09.08). Кнопка: «Бухгалтер (администратор филиала)» |

## 1. Модель данных и изоляция

**Флаги:**

- `branches.isDemo: checkbox` — ровно один демо-филиал «ФК Звёздочка» (вымышленный
  город), создаётся сидом.
- `users.demo: checkbox, saveToJWT` — на пяти демо-юзерах
  (`demo-owner@trener.local`, `demo-admin@…`, `demo-coach@…`, `demo-parent@…`,
  `demo-child@…`; домен нерутируемый). `saveToJWT` — гейты отвечают без похода в БД.

**Гейты изоляции — оба направления плюс исходящие:**

1. **Демо не видит живое.** Для `user.demo` все access-функции принудительно
   добавляют `branch = <демо-филиал>` (helper в `access/roles.ts`, вкручивается в
   существующие scoped-хелперы M5). Самая опасная роль — демо-`owner`: настоящий
   owner видит все филиалы, демо-owner обязан видеть только демо. `/admin`-панель
   демо-юзерам закрыта полностью.
2. **Живое не видит демо.** Списки филиалов/групп для обычных пользователей
   исключают `isDemo`-филиал (живой родитель не встречает «ФК Звёздочка»
   в переключателе).
3. **Исходящие наружу глушатся** (#133): `sendPushToUser` — ранний выход, если
   адресат `demo`; email демо-юзерам не отправляется; создание `Devices`
   демо-юзером запрещено access'ом (посетитель не подпишет свой телефон под
   демо-пуши). In-app уведомления — обычные строки БД, работают как есть.

**Приёмка гейтов — мутационная (#114):** каждый класс ломается тестом
(демо-owner запрашивает живой филиал → пусто; живой список содержит демо →
красный; пуш демо-юзеру → `skipped`).

## 2. Вход, «Сменить роль», лимит 5

**Вход.** Страница `/demo`: пять кнопок ролей → `POST /demo/login` → сервер
находит демо-юзера по фиксированному email → стандартная сессия через
существующий `buildAuthCookie` (magic-link-механика, `sid` в JWT) → redirect на
`roleHome` роли. Паролей на странице нет, новой auth-механики нет. Демо-юзер не
найден (сид не прогнан) → честная страница «демо готовится», не 500.

**«Сменить роль».** `AppShell` при `user.demo` рисует несмываемую плашку
«🎭 Демо-режим — данные выдуманы» + кнопку «Сменить роль» → `/demo`. Одна точка
вкрутки на все экраны; плашка одновременно маркирует витрину.

**Лимит 5.** Скрытое поле `demoGuest: checkbox` на коллекциях, куда роли пишут
из UI (точный список фиксирует план реализации); хук
`beforeChange` ставит его, когда создатель — демо-юзер. Сид пишет
`demoGuest: false` (Local API) — богатый сид в лимит не упирается; посетитель
создаёт **до 5 своих** сущностей в каждом разделе. Превышение → дружелюбная
ошибка («В демо можно создать не больше 5 — этого хватит, чтобы всё
попробовать»). Считается `count(collection, demoGuest=true)`; гонка двух
посетителей (6-я вместо 5-й) — не инцидент.

## 3. Сид и reseed

**Сид** — `lib/demo/seedDemo.ts`, вызывается из cron-роута и ручного скрипта.
Порядок: снести содержимое демо-филиала в FK-порядке → создать заново.

Наполнение (по мандату): 2 группы; ~8 детей с родителями; тренер; расписание на
неделю вперёд (даты относительные — reseed держит их свежими); 2–3 сыгранных
матча **с авторами голов** (`Matches` + `MatchComments`); чаты с перепиской;
**платежи за 3 месяца** с разбросом — оплачено ровно / долг / переплата
(`Subscriptions`/`PaymentThreads`). Имена выдуманные, не из окрестностей (урок
демо-стенда Матрицы). Паттерны — из `seed-dev.ts`, но генератор на сущность, без
сквозного PRNG (#139). Приёмка сида: двойной прогон + равный `count(*)`, и
глазами (#093).

**Reseed** — `/cron/demo-reseed` с `CRON_SECRET` (клон механики
`rsvp-reminders`), ночью MSK.

## 4. Лендинг

Кнопка на главной: «Посмотреть ДЕМО приложения (потрогать изнутри в разных
ролях)» → `/demo`.

## 5. Тестирование

- Гейты изоляции — 3 класса из §1, мутационно (#114).
- Лимит 5 — 5 создаются, 6-я отклоняется; сид лимитом не ограничен.
- Глушение пуша/почты — демо-адресат → `skipped`, `Devices` не создаётся.
- Вход каждой из 5 ролей → правильный `roleHome`-редирект.
- Финальная приёмка — глазами по живой странице (как D-017), отчёт Мозгу по факту:
  кнопка на главной, вход под каждой ролью, лимиты, «Сменить роль».

## 6. Порядок PR

Каждый мержится зелёным и не ломает прод до включения витрины:

1. Флаги + гейты изоляции + глушители (без UI — в проде невидимо).
2. Сид + cron-reseed.
3. `/demo` вход + плашка/«Сменить роль» + кнопка на лендинге (включение витрины).
4. Приёмка глазами на проде + отчёт Мозгу.

## Вне скоупа

- Отдельный инстанс/БД/схема для демо (отклонено — см. развилки).
- Пер-посетительские комплекты данных (отклонено — общие аккаунты).
- Роль «бухгалтер» как новая системная роль (используется существующий `admin`).
- Медиа-файлы в демо (аватары/фото) — сид обходится без загрузок.
