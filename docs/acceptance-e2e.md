# Сквозная приёмка бизнес-сценария

> Живой чек-лист: **прогоняется целиком** после изменений, задевающих роли, филиалы,
> расписание, чат, оплату или согласия. Каждый шаг судится по **наблюдаемому маркеру**
> у конечного потребителя, а не по коду ответа (#193: «внешний 200 ≠ работает»).
> Последний прогон и его результат — в конце файла.

## Подготовка стенда (локально)

1. Поднять Postgres (на rmz4val из агентской сессии — `pg_ctl start -D "C:\Program Files\PostgreSQL\17\data" -w`,
   профиль машины в [`machines/rmz4val.md`](machines/rmz4val.md)).
   ⚠️ **Имя БД обязано содержать `trener_dev`**: `seed-dev.ts` отказывается работать с
   любой другой («ОТКАЗ: скрипт только для dev-БД») — защита от засева прода. БД,
   названная просто `trener`, выглядит рабочей ровно до первого `pnpm seed`.
2. Поднять dev-сервер **preview-инструментом** (конфиг `web-dev`), не shell-командой:
   он же даёт логи сервера, из которых берётся ссылка magic-link.
3. Данные: сид `cd web && corepack pnpm seed`. Что должно быть в БД до старта:
   - филиал с **полными реквизитами оператора и подписанным договором** (сид даёт такой):
     без этого D-016 не даст ни приглашать родителей, ни принимать согласия;
   - **юр. документы** (`legal_documents`) — отдельной командой (сид их не создаёт):
     `cd web && corepack pnpm seed:legal`. Без неё весь
     юридический контур мёртв: на экране согласия будет «Текст согласия готовится»,
     на `/coach/legal` — «Текст договора готовится». На dev миграции не накатываются
     (drizzle-push), поэтому data-часть миграции юр. документов на стенд не приезжает;
   - **демо-филиал** — отдельной командой: `cd web && corepack pnpm seed:demo`.
     Сид его НЕ создаёт, и без него красный путь ниже пройти нельзя: `/demo/login` ищет
     пользователя по фиксированному email с `demo: true`, не находит и молча уводит на
     `/demo?state=preparing` — экран выглядит как «песочница готовится», хотя готовиться
     нечему и ждать бесполезно. Скрипт `seed-demo.ts` лежал в репозитории с самого начала,
     npm-команды к нему не было до 14.09;
   - **отрицательный контроль D-016** готовится руками: у одного филиала очистить
     «Договор поручения подписан» в админке (или завести филиал без реквизитов).
4. Учётки сида: владелец `admin@trener.local` / `devpass1234`; тренеры и родители —
   `coach@trener.local`, `parent1@trener.local` и т.д.
5. **Две роли одновременно**: родителя держать во внешнем Chrome, персонал — во встроенной
   панели (разные cookie-хранилища; правило в [`../AGENTS.md`](../AGENTS.md) «Чем смотреть на приложение»).

## Красный путь: демо-владелец не видит живую сеть

Демо-сессию получает **любой посетитель** кнопкой на `/demo` (POST `/demo/login`,
`role=owner`), а демо-владелец имеет `roles:['owner']`. Поэтому после любой правки
экранов персонала прогоняем этот блок — он ищет утечку живых данных в витрину.

Войти демо-владельцем и убедиться, что **ничего живого не видно**:

| Экран | Должно быть видно | Красный флаг |
|---|---|---|
| `/coach/requests` | пусто («Заявок нет») либо только заявки демо-филиала | email живых заявителей, ФИО детей из живых саморег-заявок, список всех филиалов |
| `/coach/staff` | только демо-персонал | `admin@…`, живые тренеры и их email |
| `/coach/import` | нет селектора филиалов; «Доступные группы» — только демо | имена живых филиалов и их групп |
| `/coach/announcements` | охват без выбора живых филиалов | имена живых филиалов в селекторе охвата |
| `/chat` → «Создать чат» | только демо-группы и демо-филиал | группы живой сети |
| `/coach/payments` | только дети демо-филиала | живые дети и суммы |

Затем **тем же маршрутом живым владельцем** — всё перечисленное обязано вернуться
(иначе скоуп зарезал не только витрину).

Правило под этим: сетевой охват решает **только `isFullOwner`**; `isOwner` допустим
как роль-гейт (`if (!isOwner(user)) redirect('/home')`), но не как «показать всё».
Автогейт от рецидива — `web/src/access/demoReadScope.test.ts`.

## Грабли самой приёмки

- **Шаг 24 не автоматизируется**: подтверждение сделано нативным `window.confirm`, а его
  не видит ни встроенная панель, ни внешний Chrome — диалог повисает и блокирует вкладку
  (лечится навигацией). Человеку мешает только это; агенту — приходится подменять
  `window.confirm` через консоль страницы. Для сравнения: отмена тренировки в
  `SessionEditor` подтверждается **в интерфейсе** (двойной клик по кнопке) — этот путь
  проверяется как есть.
- **`filter=interactive` у чтения страницы пропускает часть кнопок** (проверено на обоих
  браузерах: «✎ Изменить», «Записать оплату», «Отозвать согласие», галка согласия).
  Не нашли кнопку — перечитать деревом `filter=all`, а не считать, что её нет.
- **Клик сразу после отрисовки может не сработать** — перечитать состояние и повторить.
- **Встроенная панель на rmz4val не отдаёт кадры**, поэтому клик по координатам там
  недоступен (координаты требуют предварительного скриншота) — только по `ref`.
- Тестовые данные после прогона остаются в dev-БД (новый родитель, ребёнок, тренировка,
  сообщение, платёж). Чистить не обязательно — но следующий прогон заводит новый email.
