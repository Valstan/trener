### Проверка токенов в URL (пункт 3 «проверь») — риск подтверждён, но не эксплуатирован

Проверено на боксе (доступ к логам только через `sudo`; без него grep молча даёт «0
совпадений» — **ложный вывод**, чуть не поверил):

- формат лога `combined_host` пишет `"$request"` (то есть **с query-строкой**) и
  `"$http_referer"`; ретенция ~14 дней; лог **общий для всех сайтов бокса**, права
  `www-data:adm` 640;
- запросов к `/auth/verify`, `/join/<token>`, `/auth/complete-login` за ретенцию **0** —
  эти потоки на проде ещё не использовались; единственное `token=` в логе — чужой
  сканер на чужом vhost (`/ws-api/v2/users/me/details?token=02`), не наш;
- **Referer не утекает**: `Referrer-Policy: strict-origin-when-cross-origin` уже стоит,
  наружу уходит только origin;
- **ограничение, которое важно помнить**: `/demo/login` идёт по `/auth/verify?token=…`,
  поэтому первое же реальное использование magic-link запишет токен в лог. Лечится
  форматом лога на боксе (вне репо) либо переносом токена во fragment — решение владельца,
  не начато.
