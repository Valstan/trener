## Важный контекст

- Production: `интер.вмалмыже.рф`, сервис `trener` на `:3007`; deploy автоматически после зелёного CI на `main` (сборка — на GitHub Actions, бокс runtime-only). Миграционные PR — по [`docs/migrations.md`](migrations.md): накат ДО мержа, авто-деплой падает на guard (ожидаемо), код доезжает ручным «Deploy to production».
- **Красный `main` тихо останавливает прод.** Автодеплой висит на `workflow_run` от CI: чужой красный (даже не свой) → deploy `skipped`, без письма и без падения. 01.08 прод не обновлялся ~1,5 часа из-за дрейфа `payload-types`. При «выкатил, а на проде старое» — сперва смотреть последний прогон CI на `main`, а не деплой.
- **`NEXT_PUBLIC_*` запекаются на CI-сборке и в серверный бандл тоже** — правкой `/etc/trener/trener.env` не меняются. Ротация VAPID-пары без пересборки отвалит пуши молча; порядок — значение в `deploy-prod.yml` → пересборка → и только потом пересохранить в КАРМАН. Детали и эмпирика — в [`docs/secrets-manager.md`](secrets-manager.md).
- **Снапшот-дрейф миграций починен** в batch 13. Правило: руками миграции не пишем; если пришлось — следующий `migrate:create` чинит цепочку полным `.json`, чужую дельту из `.ts` вычищаем, верификация обязательна.
- `login_tokens.email` теперь conditional (validate по purpose) — invite-токены живут без email до привязки.
- Юридический go-live остаётся отдельным решением для каждого филиала (закрытое тестирование на вымышленных данных); M10 (S3-галереи) не начинать без решения владельца.
