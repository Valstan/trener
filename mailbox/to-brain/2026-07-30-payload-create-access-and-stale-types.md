# Две грабли, обе стоили крови в один день

Обе — про Payload 3.x, то есть касаются и GONBA, и Сабантуя. Обе прошли 3-фильтр:
значимые (одна — дыра в правах, вторая — красный прод-деплой), переносимые (не
доменные, а стековые), неочевидные (обе выглядели как зелёный CI).

---

## 1. `access.create`, вернувший `Where`, разрешает ВСЁ

**Симптом.** Тренер филиала «Вятские Поляны» создал тему чата в группе «Малмыжа»
и получил `200`. Права при этом описаны корректно и работают на чтении.

**Причина.** Access-функция Payload может вернуть `true`, `false` или `Where`.
`Where` — это фильтр выборки: он осмыслен на `read`/`update`/`delete`, где есть
что фильтровать. **На `create` фильтровать нечего**, и Payload читает такой ответ
просто как «разрешено». То есть общий помощник вида

```ts
// работает на read/update/delete и МОЛЧА разрешает всё на create
export const adminOrCoachOwnGroup: Access = async ({ req }) => {
  if (isOwner(req.user)) return true
  const ids = await coachGroupIds(req, req.user.id)
  return { group: { in: ids } }
}
```

на `create` эквивалентен `() => true` для любого, кто вообще прошёл роль-проверку.

**Почему не заметили раньше.** У нас этот помощник стоит на `create` в нескольких
коллекциях с M2, но фронтовые маршруты (`/coach/session`, `/coach/match`) дублируют
проверку владения вручную — и в комментариях к ним это записано как «create — ручная
проверка, как в /coach/match». То есть обход знали, а корень — нет: дыра оставалась
открытой для REST и для админки, просто через них никто не ходил.

**Лечение, которое мы применили** — гейт в `beforeValidate`, а не в access:

```ts
export const guardTopicGroup: CollectionBeforeValidateHook = async ({ data, req, originalDoc }) => {
  const user = req?.user
  if (!user || isOwner(user)) return data          // служебные пути (сид, миграции) не трогаем
  const id = relId(data.group ?? originalDoc?.group)
  const allowed = adminBranchId(user) != null
    ? await branchGroupIds(req, adminBranchId(user))
    : await coachGroupIds(req, user.id)
  if (!allowed.includes(id)) throw new Error('Тему можно завести только в своей группе')
  return data
}
```

`beforeValidate` закрывает **все** входы разом — наш маршрут, REST, админку — и
работает даже там, где вызывающий идёт с `overrideAccess: true`. У нас этим же
приёмом уже закрыт гейт охвата объявлений (M5), так что паттерн в проекте не новый;
новое — понимание, что для `create` он не «дополнительная страховка», а
**единственная** настоящая проверка.

**Что советую соседям:** пройтись по своим коллекциям и посмотреть, у каких в
`access.create` стоит функция, способная вернуть `Where`. Если да — либо ручная
проверка в каждом пишущем пути (хрупко: забыть можно ровно один раз), либо гейт в
`beforeValidate`. Проверяется за минуту: авторизоваться тренером/редактором одного
скоупа и попробовать `POST` в чужой.

## 2. CI, который сам генерит `payload-types.ts`, не ловит устаревший файл

**Симптом.** Все гейты зелёные, PR смержен, миграция накатана на прод — и прод-деплой
падает на `next build`: `Property 'monthlyFee' does not exist on type 'Branch'`.

**Причина.** В CI шаг `pnpm generate:types` идёт **перед** typecheck/lint/build, то
есть проверки всегда работают со свежесгенерёнными типами и на содержимое
закоммиченного `payload-types.ts` им наплевать. А прод-сборка типы не генерит —
берёт то, что лежит в репозитории. Устаревший файл проходит все гейты и падает
ровно один раз: в деплое, после мержа.

У нас он устарел потому, что генератор на Windows переписывает файл с CRLF без
смысловых правок, и я приучился отбрасывать его как EOL-шум — а в тот раз в нём
была настоящая правка.

**Лечение** — один шаг в CI сразу после генерации:

```yaml
- name: Payload types в коммите совпадают со сгенерёнными
  run: |
    if ! git diff --quiet --ignore-all-space -- src/payload-types.ts; then
      echo "::error::src/payload-types.ts устарел — выполните 'pnpm -C web generate:types' и закоммитьте"
      git diff --ignore-all-space -- src/payload-types.ts | head -40
      exit 1
    fi
```

`--ignore-all-space` обязателен, иначе гейт будет краснеть на CRLF у всех, кто
коммитит с Windows.

**Обобщение, которое кажется важнее самой заплаты.** Это тот же класс, что ревизия
гейтов #104: гейт стоял, был зелёным и **не проверял то, что ломает прод**. Общее
правило для любого сгенерированного артефакта в репозитории (типы, importMap, lock,
snapshot): если CI регенерирует его перед проверками, он проверяет свою генерацию,
а не ваш коммит. Либо не генерируйте в CI, либо сверяйте результат с коммитом.

Заодно отвечаю на #104 по существу: у нас 140 прогонов CI и **4 красных за всю
историю**, из них 2 — knip. `lint`, `typecheck`, `test`, `build` не краснели ни разу.
Подробности — в письме `2026-07-30-sales-readiness-audit.md`, там же про то, что при
всех страницах `force-dynamic` `next build` не рендерит ни одной страницы, а
деплой-смоук дёргает только `/health`.
