# План исполнения D-016

Мандат принят целиком, конструкция — ровно по твоим требованиям. Порядок чуть меняю,
и вот почему.

## Находка, меняющая порядок

Аудит перед стартом показал: **согласие сейчас не записывается вовсе на основном
invite-пути**. `acceptInvite` создаёт родителя без `branch`, а экран согласия при
`branch == null` молча редиректит мимо (`onboarding/consent/page.tsx`). Саморег-путь
(#115) на согласие тоже не заводит. То есть строить D-016 поверх текущей маршрутизации —
значит собирать подписи в экран, куда половина родителей не попадает.

## Порядок кусками

1. **PR `fix/onboarding-consent-and-loops`** — пререквизит: invite проставляет родителю
   филиал из группы ребёнка, оба пути (invite и саморег) заканчиваются экраном согласия,
   серверный гейт «родитель без согласия → на экран согласия».
2. **PR `feat/legal-docs-d016`** (один PR с миграцией, размер L):
   - Коллекция `legal-documents`: kind (processing_agreement | parent_consent), version,
     body (markdown), content_hash (sha256 в beforeChange), published_at;
     unique(kind, version); после публикации body/version неизменяемы — только новая
     версия. Правка через админку, не через релиз.
   - Коллекция `legal-signatures` — неизменяемый журнал: kind, документ, снапшот
     content_hash, филиал, подписант, дети[], action (signed | withdrawn), UTC, IP,
     user-agent, **снапшот реквизитов филиала** на момент подписи. create — только
     server-mediated маршруты; update/delete — никому, включая owner.
   - Флоу школы: экран «договор поручения» с подставленными реквизитами филиала +
     кнопка подписания; до подписи филиал не может приглашать родителей.
   - Флоу родителя: экран согласия читает активную версию из БД; подпись пишет журнал.
   - Жёсткий гейт вместо мягкой плашки «Тестовый контур»: `branchCanAcceptConsents` =
     реквизиты заполнены (уже есть вычисляемый `isOperatorFinalized`) + договор подписан.
   - Отзыв согласия — экран в `/account`, новая журнальная запись `withdrawn` + пуш owner.
   - Тексты пишу из реальной схемы БД (Users/Players/Rsvps/чаты/Subscriptions) с
     перечислением технически существующего: экспорт субъекта, каскад удаления,
     offsite-бэкап, РФ-хранение. Твой тест «покажу ли текст, под которым подписался
     родитель год назад» — проходит по построению (hash + неизменяемые версии).
   - Туда же: догоняю экспорт (`export-data-subject.ts`) и каскад удаления до текущей
     модели (payment-*, chat-messages, match-comments, question-messages,
     child-registrations) — чтобы договор не обещал больше, чем код умеет.
3. Осознанное решение (зафиксирую в PR): новая версия документа **не** форсирует
   повторное согласие уже подписавших — это отдельный будущий шаг по требованию.

## Оценка

Оба PR — в ближайшей серии сессий (текущая — большая доводка продукта к продаже,
D-016 в ней третьей волной из шести). Отчёт о выкате — отдельным письмом по факту.
