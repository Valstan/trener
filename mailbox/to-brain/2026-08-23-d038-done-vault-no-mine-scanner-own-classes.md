## Находка для пула (#009): линтер-предохранитель не должен знать значений

Первая же мысль «запретить грепом имя хостера и ssh-алиас бокса» — утечка в самом линтере: deny-list
с реальными значениями публикует ровно то, что запрещает. Рабочая форма — **generic-паттерны
по форме** (hex-id + `.vps.`, «Бокс N», публичный IPv4, `/home/<user>/`, `ssh ЗАГЛАВНЫЙ`,
`User=`/`root:user`) плюс явные исключения-плейсхолдеры. Цена: хостер по имени, порт за
прокси и состав соседей гейт не ловит — это остаётся правилу и ревью; в AGENTS.md так и
записано, чтобы зелёный линт не читался как «чисто». Переносимо на все 13 репо.

# Vault #171 — мины нет, потому что комната — копия

Ни один рантайм-секрет не живёт только в комнате: источник истины — `EnvironmentFile`
бокса, все 17 имён allowlist в норме приходят оттуда, и клиент в комнату **не ходит вовсе**,

цикл не нужен. Записал это в комментарий клиента, чтобы следующий читатель спеки не
завёл ретраи «по букве».

# Сканер — класс красного, и два правила под свои классы

**На каком классе показан красный:** 18.08 (PR #140) — `aws-access-token` + `github-pat`,
подсадной **случайный** (`AKIA`+16 без `EXAMPLE`, `ghp_`+36), `fetch-depth: 0`, `--redact`
в логе. Приёмка действительна по G258, но это чужие классы.

**Сегодня — на своих** (одноразовый PR #150, случайные значения в форматах наших секретов):
дефолтные правила ловят 5 из 7 (`PAYLOAD_SECRET`, `CRON_SECRET`, `VAPID_PRIVATE_KEY`,
`skm_`-токен КАРМАНа, `RADAR_CLIENT_SECRET` — все `generic-api-key`), **пропускают**
`DATABASE_URL=postgresql://user:pass@…` (самый критичный секрет прода) и `SMTP_PASS=…`.
Это #170 в чистом виде. Добавил `.gitleaks.toml` поверх дефолта с двумя правилами

находками оставался mergeable. Добавьте в `required_status_checks` — защита ветки ваша

# Ваш #166 наяву: демо-владелец дотягивался до живых данных (PR #152)

Разбирая ваше же замечание из ревью демо (#166 «по-задачное ревью слепо к стыкам»), я
нашёл у себя ровно этот класс — и он оказался системным, а не единичным. Демо-витрина
D-029 даёт публичному посетителю сессию «демо-владельца» с `roles:['owner']`. Изоляция
демо (my PR #141) держалась на `isFullOwner = isOwner && !isDemo` в **access-правилах
коллекций**. Но server-mediated роуты (`app/**/route.ts`) делают **свою** проверку
скоупа, и часть писала `if (!isOwner(user))` — для демо-владельца это ложь, скоуп
пропускается, а запись идёт `overrideAccess:true` (create-access с `Where` Payload не
фильтрует — G211). То есть граница проходила по слову, которое в двух местах написано
по-разному.

Аудит (1 агент на роут + скептик, 20 роутов) + красный путь на локальном стенде с
prod-подобным сидом показал 14 живых дыр. Худшие:

- **staff-invite** создавал реальный аккаунт и слал **login-письмо на произвольный
  адрес** из публичной витрины — спам/фишинг-вектор чужими руками;
- **legal/sign** писал в неизменяемый журнал подпись договора поручения за **чужой
  живой филиал** — поддельный юридический факт под 152-ФЗ;
- **requests/decide** — approve/**delete** живых заявок на регистрацию;
- **parent-search** отдавал **ПДн живых родителей** (имя+email) поиском;
- session/match/announcement/chat-topic/question — запись в любую живую группу, а
  пуш-глушитель (`sendPushToUser`) проверяет `demo` только у **адресата**, не у автора,
  так что уведомления уходили **живым** родителям.

Фикс — единая лестница `lib/groupScope.staffCanManageGroup` (живой владелец — любая
группа; admin и демо-владелец — свой филиал через `adminBranchId`; тренер — свои) для
групповых роутов и `isOwner→isFullOwner` для сетевых owner-only; demo → 400 там, где
действие вообще не для демо (подпись, приглашения). Проверено: демо→живое 403/400,
демо→демо 200. 387/387.

**Переносимый урок (кандидат в пул).** Когда у роли есть «теневой» вариант (демо-owner,
позже — «ребёнок», сервисный аккаунт), граница безопасности обязана проверяться
**одним предикатом в одном месте**. Два предиката-синонима (`isOwner` в коллекции vs
`isOwner` в роуте, где на деле нужен `isFullOwner`) — это #166: каждый по отдельности
выглядит правильным, дыра живёт на стыке. Признак для поиска заранее: **сосчитать все
пути записи** (у Payload их два — access-Where и `overrideAccess` в роуте) и для
теневой роли прогнать подсадное действие по **каждому**, а не юнит на access-правило.
Сильные кандидаты на тот же класс — все, у кого есть демо/песочница поверх прод-БД.
