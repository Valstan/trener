# Рукописная миграция без .json = мина для следующего migrate:create

Сегодня наступили, вытащили ногу, делюсь (3-фильтр: значимо для всех
Payload-проектов с миграциями, переносимо 1:1, неочевидно до первого раза).

## Симптом

`migrate:create future_matches` для правки двух полей **matches** сгенерировал
миграцию, которая заодно `ADD COLUMN` девяти колонок **branches** — уже месяц
как существующих на проде. Применить как есть — упало бы на «column already
exists» прямо в CI-накате.

## Механика

Drizzle-генератор диффит не живую БД, а **цепочку `.json`-снапшотов** рядом с
миграциями. Наша прошлая миграция (`branch_operator`, batch 12) была написана
**руками** — `.ts` без парного `.json`. Для генератора этих колонок «ещё нет»,
и он честно дописывает их в следующую дельту. Это ровно тот «снапшот-дрейф
(#017)», который у нас в runbook значился теоретической граблёй — теперь
воспроизведён.

## Лечение (двухходовка)

1. `.json` свежесгенерированной миграции **оставить как есть** — он полный
   снимок текущей схемы и чинит цепочку снапшотов раз и навсегда.
2. Из `.ts` **вычистить чужую дельту руками** (оставить только свою), потому что
   чужие колонки на проде уже есть.
3. Обязательная верификация после ручной правки — прогон всей цепочки на чистую
   БД и дифф со схемой dev-push (у нас в `docs/migrations.md`, секция
   «Верификация»); наш прогон дал IDENTICAL с точностью до порядка колонок
   (порядок различается легитимно: push добавляет колонки в конец, миграции —
   в своём порядке; сравнивать стоит сортированным диффом).

## Мораль

Пишешь Payload-миграцию руками — либо не пиши (сгенерируй и поправь), либо
знай, что **следующая** сгенерированная миграция принесёт твою дельту второй
раз, и её автору придётся понять почему. Пункт «руками = без .json = дрейф»
стоит добавить в REFERENCE к рецептам Payload-миграций (#017), если его там нет.
